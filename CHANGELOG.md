# Changelog

This repo ships independent Claude Code plugins that are intentionally version-less — every commit to the marketplace is a new version, so users on auto-update always track the latest. Entries are therefore anchored by **release date**, newest first, and grouped by plugin.

## Unreleased

### agrev (new plugin)

- **add `agrev`**, moved here from a standalone skill in `~/.claude/skills/`, where it had no history. It opens a markdown document in [plannotator](https://github.com/backnotprop/plannotator), shown in an agterm session right after the agent's, and runs the review in rounds: the user annotates and sends feedback or approves, the agent edits the document and opens the next round with its replies pinned to the phrases they answer. Moved unchanged; as a plugin skill it is invoked as `/agrev:agrev` instead of `/agrev`.
- picking which document to review no longer forbids the AskUserQuestion widget; the user's own instructions decide how a question is asked.

### huddle

- **every choice opens a page.** In the first two days after install my sessions asked 89 questions through the question widget and 3 through huddle (counted from the session transcripts). The widget questions were the ones that need context most — sequencing a spike, where a shopper's season lives, palette licensing, what a taxonomy field describes — and each arrived as three short labels. Two rules had squeezed huddle out: the skill said a page is for questions where seeing beats reading and that short-answer questions stay in the terminal, and my rules sent every 2–4-option choice to the widget with an exception only for "structural" choices. The skill now takes every question that asks the user to choose or approve, two-option choices included, and leaves only typed answers and a bare go-ahead on a just-described step to the terminal; the description and the "When to ask" section say so. The README carries the matching rules line, which overrides a widget rule inside agterm. Measured with my real configuration and the real launcher, three `claude -p` runs each: architecture choice, code judgement and a two-option suite choice went to huddle 3 of 3, a rename confirmation and a "which Jira ticket?" question stayed in the terminal 3 of 3, and the widget was used 0 times in 15; the narrower exception had left the two-option choice in the terminal. Evals: `huddle-silent-plain` becomes `huddle-fires-small-choice` (two options, each saying what it costs and catches) and `huddle-silent-free-text` is new; across the five cases the three positives opened a page 3 of 3 with the plugin and 0 of 3 without, and both negatives stayed in the terminal every time. The code case's judged "source not pasted" check became a regex over the trace, since an llm judge sees only the first and last 12 messages and missed the huddle call in longer runs (it failed 2 of 3 runs whose regex check passed); with it, the case scores 1.00 against 0.33 without the plugin.
- **a page carries more context than a list, never less.** Approving a plan through huddle showed three bare options, "Story 3", "Story 4", "Story 5", and none of the evidence. The spec had it: the agent put each question's evidence and the stories' text under a question's `context`, and the page reads `context` only at the top level (inherited from upstream; checked by rendering the same spec with upstream's runtime), so every question's evidence was dropped without a word. The skill had invited it by listing "`context` / `body`" as one field. Three fixes. A question's `context` now renders like its `body` in a multi-question spec. `check_spec` rejects any key the page does not read, at the top level and on questions, options and controls, naming the nearest valid key and where it belongs (`'subtitel' (did you mean 'subtitle'? it belongs at the top level or on an option)`); a key starting with `_` stays the author's own. And an option whose label only counts (a counting word plus a number or letter: "Story 3", "Option B", "step 2") and carries nothing else is refused with a message telling the agent to put the item's text on the option; a bare number or letter passes, since 3 replicas or size M is the answer itself. SKILL.md gains a "Carry the context" section and a send check: could the user answer from the page alone? The original page now fails with that message, and the same spec with the stories' text on the options renders every piece of evidence (checked in headless Chrome). Tests: 71 checks, adding the four rejections, a carried-text pass, and a browser check that a question's `context` and `body` both show; with upstream's runtime that check fails.

### peer-planning (new plugin)

- **add `peer-planning`**, moved here from a local directory marketplace where it had been in daily use. `/peer-planning:make` writes a plan whose tasks are outcome-level slices for a capable executor; `/peer-planning:exec` runs it as a two-agent loop in an agterm split: a subagent implements each task, Codex in the other pane reviews the diff before the commit and is cleared before the next task, and every step lands in a jsonl event log with a live monitor page. It is moved as it was, with one change: the `peer_planning_pytest` module that feeds the monitor's test panel now lives outside the plugin, in `~/.local/lib/agterm-pytest/` next to agterm's `agterm_hud`, since every pytest on the machine loads it through `PYTHONPATH` and `PYTEST_ADDOPTS`, not only the runs of this plugin. Without that module the monitor shows no test progress.
- it depends on things this repo does not ship: [agterm](https://github.com/umputun/agterm) with its [two-agent-chat](https://github.com/umputun/agterm/blob/master/cookbook/two-agent-chat/README.md) recipe (`peer-chat.py` and the `peer-chat` skill), Codex, and [revmux](https://github.com/umputun/revmux) for the closing review.
- **no longer needs `planning@umputun-cc-thingz`.** The branch review after the last task used to borrow that plugin's review and fixer playbooks, its default-branch script and its commit and progress scripts, found through `installed_plugins.json`. It now has its own: `references/review.md` runs revmux rounds (the `comprehensive` profile first, then `final` re-checks, up to five), adapted from the project playbook that had been doing this job in practice, and a "Fix review findings" prompt sends each round's findings to a fresh subagent that commits through the project hook and carries the project rules. A project replaces the review with `.claude/peer-planning/review.md`. The rules resolver reads only the project's `.claude/planning-rules.md`; the planning plugin's user-level fallback is gone. `exec` finds the default branch from `origin/HEAD` itself.
- `make`'s intent questions and `exec`'s plan picker no longer forbid a question widget; the user's own instructions decide how a question is asked.
- **a `run.start` that `run-records.py` cannot read no longer aborts housekeeping.** `exec`'s setup step told the orchestrator to log `run.start` with only `session` and `tasks`, while `references/event-log.md` and the scripts expect `plan`, `work_path`, `branch` and `executor` as well. `run-records.py --landed` then read the missing `plan` and one finished run took the whole listing down with a `KeyError` (reported from a run of 2026-10-20; the monitor had shown that run without its plan, branch or executor for the same reason). The setup step now spells out the full `log-event.py` command; `log-event.py` refuses a `run.start` missing any of those fields or carrying an absolute plan path, so the record fails when it is written rather than at cleanup days later; and `run-records.py` names a run it cannot read on stderr and lists the rest. `tests/test-peer-planning.sh` covers both scripts in a throwaway clone and runs in CI.
- **Codex is told where the work is, and to run its commands there.** Every message to Codex already named `WORK_PATH` as an absolute path, but the review request only said to see the diff "there", and Codex's own directory is wherever the user started it, usually the main checkout, which it cannot change for the session; a bare `git diff` there reviews the wrong tree, and an LGTM over an empty diff reads like any other. The setup check, the discussion opener and the review request now say the work happens in `WORK_PATH`, not necessarily where Codex was started, and ask it to run every command there, with the `git -C WORK_PATH` commands spelled out in the review request.
- **an LGTM over the wrong tree is caught.** Every review reply now ends with `Changed:` and the paths Codex saw in `WORK_PATH`; the orchestrator runs `git -C WORK_PATH status --short` itself and compares before it logs the verdict. A mismatch is logged as `review.mismatch`, the review is asked again, and a second mismatch on the same round goes to the user. The monitor shows the mismatch and the renewed wait on Codex.
- the completion report names `/git:wrap-up` as what follows finalize.
- **`exec` runs in a fresh session.** Every orchestrator call pays for the whole context it holds. Over three runs of 2026-10-29, priced at list rates, the orchestrator was 36-61% of each run's Claude spend, and 79% of its own cost went to writing its context back into the prompt cache after misses. Each run entered `exec` holding 300-340k tokens left over from `make` and its revmux round in the same session, and grew to 520-650k by the end. One session kept for 12 hours after `run.end`, for follow-up questions, finalize and wrap-up, cost $124, more than its run's whole task phase ($119). `make` now ends by suggesting `/clear` and then `/peer-planning:exec <plan>`; `/clear` keeps the agterm session, so Codex stays in the pane next to it. `exec` has a new first setup step: when the conversation already holds other work, it stops and suggests the same restart, and goes on only when the user says so. The completion report sends follow-up questions, finalize and wrap-up to a fresh session as well.
- **`exec` does not run under `/goal`.** A goal is checked after every turn that ends with no background work running ([docs](https://code.claude.com/docs/en/goal)), and in `exec` that is every wait on Codex. The check re-prompted the orchestrator, which then read Codex's pane against its Waiting rule: 76 extra calls in one run of 2026-10-29, 236 in another. One session's `/usage` also showed $104 of model calls that are not in its transcript, over 57 goal checks, against $30 over 5 checks in another run. They look like the checks themselves, each of which sends the whole conversation to the small fast model. `exec` needs no goal, since Codex's messages and the subagents' returns already wake it, so its first setup step now stops under an active goal and asks for `/goal clear`, or `/clear`, which removes the goal too. A goal file that ran `make` and then `exec` in one session now stops at `exec`.
- **the `/goal` refusal answers in one line.** A goal re-prompts the refusal too. Claude Code ends a run of Stop-hook re-prompts after eight in a row with no tool call between them ([hooks guide](https://code.claude.com/docs/en/hooks-guide), "Stop hook hits the block cap"; `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` changes the number), and every tool call starts the count again. So `exec` answers each re-prompt in one line with no tool call, not even a look at Codex's pane, and control comes back after eight. In the measured runs, a look at the pane after each re-prompt is what kept the re-prompts coming.
- **Codex's review items go to the implementer unopened.** The orchestrator used to open the code behind every must-fix item before passing it on. Over the three runs of 2026-10-29 Codex raised 16 must-fix items in first-round reviews and 4 in re-reviews, the orchestrator disputed none, and no run logged a ruling. Priced from the orchestrator transcripts, those checks were 13-26% of the orchestrator's task-phase cost, and they are what pulled code and path-scoped rules into its context. The implementer already had the code open, and its "Apply Codex's review" prompt already told it to apply each item or say why one is wrong. The orchestrator now relays the items verbatim. The implementer applies or refutes each one and names its refutations in a `REFUTED` line, which the re-review request carries to Codex as disputes. A task discussion still verifies every claim Codex makes.
- **the implementer writes its own report file.** Each report used to reach the orchestrator in full and go back out verbatim to `msgs/NNN-claude-review.md` for Codex: in one run, about 120k characters in and 47k written out again. The implementer now writes `RUN_DIR/msgs/NNN-implementer-report.md`, the review request names it, and the final message is five lines: the status, the report's path, whether validation passed, and one line each of decisions and deviations. A fix round adds `REFUTED`. The orchestrator opens a report only when it says BLOCKED and the evidence goes to the user.
- **the branch review steps back instead of chasing one function.** In one run, all four revmux rounds found a defect in the same function, at four different lines, with gating counts 1, 2, 1, 0: a design gap patched one case at a time. `references/review.md` Step 7 had a stop rule for this, but it did not fire at round 2, where the count rose, because it asked for the same mechanism in the same place and the orchestrator read the two findings as different mechanisms. A repeat is now any gating finding in the same function or symbol as one of the previous round's, whatever its mechanism. When the rule fires, the finding goes to Codex, which otherwise takes no part in the branch review, as a design discussion over whether the symbol's design is right, and the fixer then builds the agreed design. A symbol gets one discussion; if the rule fires on it again, the phase ends as before. The discussion logs `discuss.*` with `stage=review` and `iteration` in place of `task`, and the monitor's ruling banner names the branch review when a stalled discussion has no task.
- **Codex's per-task review is an outcome check.** The review request asked Codex to review against the approach, the "Done when" list and the plan's Decisions, and its first-round items took in a project-rule break and a spelling fix as well. It now asks whether the change delivers those, whether its evidence exercises what it claims (read the tests, fixtures and producers it relies on), and for any correctness defect seen on the way. An existing caller or inverse operation the change leaves inconsistent is a must-fix. General rule, architecture and style issues are left to the branch review. Claude and Codex agreed this between them; it is a pair-settled position, not a measurement. Codex sorted the 16 first-round items of the three runs of 2026-10-29 and put 13 inside the narrower check. An import-rule break, a spelling fix and at most one detailed test review move to the branch review, where a minor fix is no longer re-checked item by item. Codex called this a judgment of scope, not a prediction of what the check will catch. Nothing measured yet shows that the narrower check and the branch review together catch what the full review did. Considered and not adopted, as unpriced: a Codex triage before every task, a periodic plan checkpoint, and a line flagging what a task means for later ones.
- **`exec` writes a full-suite record that finalize trusts.** When an implementer's last validation ran the full suite and passed with passed + skipped == collected, and nothing but the plan file changed before its commit, its reply to the "Commit" prompt carries a `FULL-SUITE:` line. The orchestrator then writes `FULL-SUITE PASS sha=… passed=… skipped=… collected=… command=…` into `progress.md` with that commit's SHA, the one form `/git:finalize-feature-branch` reads.
- **the branch-review fixer writes its own report file too.** Its FIXES and DECISIONS came back to the orchestrator in full and were copied into `progress.md`. The fixer now writes them to `RUN_DIR/msgs/NNN-fixer-report.md` and returns four lines: the commit with the hook's result, whether validation passed, the fixed and false-positive counts, and the report's path. `progress.md` gets one line per iteration with the path, commit and counts. The next revmux round gets the earlier fixer reports in its context next to `progress.md`, the next fixer reads them, and the completion report takes the fixers' decisions from them. A fixer whose commit failed ends the review phase.
- **the whole suite runs once, in a closing `exec` stage after polish.** In one run of 2026-10-29 the plan's verify task ran the whole suite, then the branch review's and polish's fixes landed on top, and finalize ran the suite three more times: once finding two regressions from those later fixes, once after fixing them, and once because another lane landed meanwhile. That suite takes 18-22 minutes alone and 41-48 beside another lane's. For the same reason the full-suite record added earlier in this release almost never matched: commits always landed after the verify task. `exec` now ends with a suite stage after polish. A fresh subagent runs the whole-suite command, the one the plan's Execution section names or else the project's agent docs, traces each failure to the commit that broke it and says whether it is a regression or an outdated expectation, fixes it and reruns until green, appends the project's suite record, commits, and reports the `FULL-SUITE:` line the orchestrator turns into the record. The record now comes only from this stage, so the per-task "Commit" prompt no longer carries the line. Fixes made in the stage get no revmux review; before, the fixes finalize made for a red suite got none either. The completion report gives the stage's runs, failures with their causing commits, and whether the record was written. The monitor shows the stage as "Whole suite". When neither the plan nor the project's agent docs name a whole-suite command, the stage is skipped and the completion report says so.
- `make`: **the verify task no longer runs the whole suite.** The plan template's next-to-last task keeps the story and Done-when check and any targeted tests. The Execution section names the whole-suite command once, for `exec`'s closing stage, and the rules list names the suite record that stage writes.

### huddle (new plugin)

- **add `huddle`** (adapted from [skkap/claude-skills](https://github.com/skkap/claude-skills) at `29d6db7`, huddle 1.0.0, MIT — see [`NOTICE`](NOTICE)). Inside agterm the agent asks a question as a page in an HTML overlay over its own session — options that are diagrams, wireframes, design samples or charts, trade-offs side by side, sliders with a live preview, several questions with a review — and reads the answer back as JSON. Before adopting it I rendered all ten templates and five demos and loaded each in headless Chrome (no runtime error, every mermaid diagram drawn) and ran a live round trip on agterm 0.35.1; the runtime is kept as published. The changes are in the launcher and the skill text.
- the launcher is **`bin/huddle`**, a bare command on the Bash tool's `PATH` (plugin `bin/` directories have been on it since Claude Code 2.1.86), pre-authorized by `allowed-tools: Bash(huddle *)`. Verified in a `claude -p --plugin-dir` run with no Bash grant: the skill loaded and `huddle templates` ran. Upstream defined `H=${CLAUDE_SKILL_DIR}/scripts/huddle.py` once and used `$H` in later calls, where it is empty because the Bash tool does not keep shell state; writing the substituted path on every line would also have fixed that, so the case for `bin/` is the bare `huddle wait <id>` a later turn can type and the short allow rule. The `allowed-tools` grant lasts only for the turn that loads the skill, so the README tells non-auto-mode users to add `Bash(huddle *)` to `permissions.allow`. Kept as its own plugin rather than folded into `decide`: claude.ai and Cowork refuse to install any plugin with a top-level `bin/` (harmless for huddle, which needs agterm anyway), and `decide` is pure markdown that works there.
- **unattended guard** — a `claude -p` run started from an agterm shell inherits `AGTERM_ENABLED=1` and gets `CLAUDE_CODE_SESSION_ATTENDED=0` (both measured), so upstream would open a page inside ralphex or a plan executor and block it for 570 s. huddle now exits 3 `unattended` and opens nothing; the skill also tells subagents to return their question to their caller, which only the instructions can enforce because a subagent shares its parent's attended flag. The variable is undocumented (not on the env-vars page as of 2.1.296; its logic was read from that binary), so only an explicit `0` refuses — if a later version drops it, the guard goes quiet instead of blocking attended sessions.
- **failures name themselves** — `overlay already open` becomes exit 5 `busy`. huddle then looks up the session's `htmlOverlays` in `agtermctl tree --json` (for its own window), and when the overlay in the way is a page under its own output directory, the reply carries that `pageID`, so an agent whose earlier question timed out — its id lost with the cut-off call or a compacted turn — waits on it instead of asking again or leaving it stranded. The lookup compares real paths: agterm reports the file as `/tmp/…` while macOS `TMPDIR` names `/private/tmp/…`. Another tool's overlay gets no id and a rule never to close it. `huddle wait` treated every agterm reply except `no such page` as "keep polling", so `invalid page id` and a stopped agterm both spun 570 s and then reported `pending`; it now fails at once on `ok: false` and after five unreadable replies. A question or option that is not an object, or `options` that is not a list, raised a Python traceback; each is now a JSON error.
- **mermaid is pinned by hash** — the bundle comes from jsDelivr and is inlined into a page that runs with agterm's bridge, which can type into terminals. It is checked against jsDelivr's own published sha256 (`07e37dfa…`, matched against the downloaded file) on download and on every read of the cache; a mismatch refetches once, then shows diagrams as source with a stderr line.
- **`file` blocks** — `code`, `diff`, `md` and `mermaid` take `{"file": …, "lines": "40-62"}` and read the text at build time; a code block from a file gets its path and range as title, numbered lines (`start`, also settable by hand) and its extension as `lang`. A missing file or an out-of-range `lines` is an error rather than an empty block, because the user is deciding on that code, and so is a whole file of more than 300 lines as `code`.
- **the "asking" glyph survives status hooks, through a Stop hook.** Hooks that post a status after each tool call and at turn end (here `truthful-lights`: `active --blink` on PostToolUse, and at Stop a machinery scan that reads the waiting `huddle` process as running work) covered a background question's glyph, so the sidebar said working while a page waited. The first fix polled: `wait_page` re-posted the asking status once the glyph had sat unchanged for a while. Review found its cost — hooks post only at a call's edges, so any long tool call read as quiet too, and each one flipped to asking mid-call (replaying a configured Blocked sound) — and a configurable window only made that rarer. The plugin now ships `hooks/hooks.json` with a Stop hook, `huddle hook-stop`, because Stop is the one exact moment: the turn is over and the page is still up. It finds a huddle page open on its session through `agtermctl tree` and re-posts asking with `--auto-reset` at 0.5, 1.5, 3 and 6 s whenever another hook has posted over it, stopping once the page is answered or closed: Claude Code runs matching hooks in parallel and in no fixed order, so it cannot simply post last, and a Stop hook slower than 6 s still wins. It is declared `"async": true`, so the turn's end does not wait on it (debug log: "moved to the background (4ms)"), and its command is a shell guard, `[ -n "$AGTERM_SESSION_ID" ] && command -v python3 … && exec …/bin/huddle hook-stop; exit 0`, so a session outside agterm or a machine without `python3` never starts Python or sees a hook-error notice. It never prints and always exits 0. A first version spawned a detached child from a synchronous hook; review pointed out that `async` does the same with less code. Not covered: Stop does not run after a user interrupt (Escape). Measured on 2.1.296 with a stand-in async Stop hook in a two-turn `--input-format stream-json` run: the hook started at the first turn's end ran its full 6 s although the second prompt arrived 0.5 s later, so an async Stop hook outlives the next prompt; a turn starting within 6 s of a turn end with a page open may therefore see asking re-posted over its own status until its next tool call, which is true while the question is open. Verified live on agterm 0.35.1 through the `hooks.json` command itself: blocked by the first recheck, re-posted over a simulated slower hook by the 1.5 s recheck, exit 0, no output, no process left after the answer. The polling and its `reclaim` setting are gone. A question that times out (exit 4) also posts its asking status with `--auto-reset`, so the user's visit clears it.
- **measured against real configuration, not only evals.** Eval runs load no personal instructions and cannot run the launcher, so thirty-three `claude -p --plugin-dir` runs with my real configuration (rules included) checked the two things they cannot: whether a personal "ask as numbered lists, never a widget" rule lets huddle fire, and whether the real launcher accepts the specs the agent writes. The unattended guard made these runs safe (it validates the spec, then exits 3 without opening anything), and `AGTERM_SOCKET` pointed nowhere as a second guard. With the rule as written: 0 of 9 tries (visual, code, plain). With an exception line appended to the system prompt, a first wording fired on code (3/3) but not on the architecture question (0/3, "the user asked for one plain question"); a second wording that names what the agent is about to do fired 3/3 and 3/3 and stayed quiet 3/3 on the plain question, and the same line as a rules file gave the same 3/3, 3/3, 0/3. Every spec passed the real launcher's validation; every visual one used a side-by-side layout with three or four mermaid diagrams, and every code one used a `file` block. The README carries the line.
- smaller: `q` options take a third `|why` field for the recommendation's reason; `api.select` on a single-choice question replaced nothing and added a second selection; code-block titles are no longer uppercased (they are paths); the description is cut from 1051 to 801 characters and leads with when to use it; a "when to ask with a page" section sends plain text questions to the terminal and defers to the user's own instructions; exit 3 says "ask in the terminal" instead of naming `AskUserQuestion`; American spelling throughout.
- `tests/test-huddle.sh` is the repo's first shell test, picked up by CI's existing glob: it renders every template and demo; checks eleven malformed specs fail with the JSON error contract; covers both exit-3 guards (unattended, no agterm), `file` blocks and `q` parsing; drives `wait_page` and the busy branch against a stubbed `agtermctl` (an agterm error and a silent agterm each end the wait at once, the busy reply names only a huddle page) and the Stop hook on a fake clock (it re-posts over a slower hook, stops once the page is answered, leaves an asking glyph alone, does nothing without a huddle page, and is silent with exit 0 outside agterm; its `hooks.json` guard exits 0 silently with no agterm session and with no `python3`; with a single recheck the race case fails); CI's manifest step now also parses every `hooks/hooks.json`, and a truncated one fails it; runs `node --check` on the runtime; and loads every page in headless Chrome when one is present, failing on an `.hd-err` node or on any diagram not drawn — a stripped-mermaid page fails it with "0 of 4 diagram(s) drawn". A missing browser, node or mermaid download prints `SKIP`, never a pass. 63 checks locally, none skipped.
- reviewed with a second Claude session acting as reader under the pair rules; it agreed with the positions, corrected the reason given for `bin/`, and priced four of the changes above: the busy page id, the 300-line cap, the stubbed agterm tests and the diagram assertion.
- `evals/` holds four `claude plugin eval` cases: two where the agent should reach for a page (an architecture choice; a judgement on code, which must arrive through a `file` block) and two where it must not (a plain one-line question; a yes/no on a file rename). What an eval run can see bounds what they measure, all checked on 2.1.296: `huddle` never executes there (the plugin's `bin/` is not on the run's `PATH`: `command not found`), no `AGTERM_*` variable reaches the run (only an allowlist and `EVAL_*` pass, and `execution.env` rejects other keys), and no personal or project instructions load. So they measure whether the skill leads the agent to try `huddle` and how good its spec is, read from the trace. Final run, 24 runs, none errored, $2.78: fires-code 0.93 with the plugin against 0.00 without, fires-visual 0.92 against 0.25, both negative cases 1.00 in both arms with no `huddle` call. Two things the runs caught on the way: a `plugins: [huddle]` line fails to load with a path target (the field takes directories relative to the case), and `arm: with-only` graders are left out of the score under a baseline arm, which had hidden that the skill was not firing at all.
- **the agent no longer checks for agterm; huddle does.** The first eval round, with a description that kept upstream's `AGTERM_ENABLED=1` condition, showed the agent spending a Bash call on `echo $AGTERM_ENABLED`; where that call was not permitted it asked in text and never tried `huddle` (0 of 6 runs). The description and the "when to ask" rules now say to run `huddle` without checking (6 of 6 tried). That is only safe if `huddle` opens nothing where there is no agterm, so the browser fallback outside agterm is now opt-in (`--browser`, or `"browser": true` in `~/.config/huddle/defaults.json`): a plain terminal gets exit 3, `status: "no-agterm"`. `HUDDLE_NO_BROWSER` is gone, since nothing opens by default.

### pyrefly-lsp (new plugin)

- add `pyrefly-lsp` plugin — registers a [pyrefly](https://pyrefly.org/) Python language server (`pyrefly lsp`, stdio by default, so no `--stdio` flag) through the same discovery wrapper shape as `basedpyright-lsp`: project `.venv/bin/pyrefly` first, then `uv run --project <root> --no-sync pyrefly`, then a global binary, then a non-zero exit with an install hint; it never auto-installs. It exists as a **sibling to `basedpyright-lsp`, not a replacement** — the invariant both plugins serve is that Claude's diagnostics agree with whatever type checker gates the commit, and that gate is a per-project fact, so the choice has to stay per-project too. One deliberate difference from the basedpyright wrapper: this one `cd`s to `${CLAUDE_PROJECT_DIR}` before exec, because pyrefly resolves *both* its config (`pyrefly.toml` / `[tool.pyrefly]`) and a project-root venv by walking up from the cwd, and the LSP subprocess cwd is undocumented — basedpyright takes its roots from the `initialize` request and doesn't care. Both plugins declare `.py`/`.pyi`, and per the plugins reference the first server registered claims the extension while the other never starts (with a `/plugin` warning naming the winner), so enabling both is a silent coin-flip rather than an error — the README says enable one.

### tracking (new plugin)

- **replace `log-issue` with `backlog`** (adapted from [umputun/cc-thingz](https://github.com/umputun/cc-thingz)'s `workflow:backlog`, MIT — see [`NOTICE`](NOTICE)). The register moves from `docs/issues/` to `docs/backlog/` and the skill goes from write-only to the full lifecycle: read, verify, work, append, drop. What his design fixes in ours, in order of weight: the `README.md` **index table is gone** — it was a second list of the same thing, because two lists of the same thing always diverge, and every delete had to remember the row; items are **slug-named** after the defect instead of `PREFIX-NNN`, so a commit can cite one and dedupe is a filename check (the subsystem prefix was a per-session judgment call, so the same defect could land under two IDs); there is now a **dedupe step** on `where` then slug, because a pre-existing defect resurfaces in every review that touches its file; `worth: yes | later | no` replaces `type: issue | open_decision | future_work` — the old field classified what kind of thing an item was, the new one classifies the only thing a deferred list needs to know, and `no` is new: a decided-not-to-fix kept so it is not rediscovered and re-argued (in the old model a "no" was deleted and came back); a **read mode** exists at all — list ordered `yes` → `later` → `no`, oldest first, every `where` verified against the tree and reported stale rather than as work, then fix/drop/leave via `AskUserQuestion`, with `/tracking:backlog <slug>` to jump to one item; a **branch guard** refuses to write onto a non-default branch without asking, since a note filed on a feature branch is swept into that PR or dies with it; and filing checks `git diff --cached` for pre-existing staged work, stages exact paths, and offers commit and push together rather than leaving the file uncommitted on whatever branch was checked out. Kept from ours, where his is looser: the **admission gate** and where a rejected finding goes instead (fix now / the dated review that owns it); the **body contract** — the concrete run with real values, the misreading to prevent, and for a `later` the options with costs plus a recommendation, which is what lets the owner decide from the file instead of re-investigating; and **symbols over line numbers** — his `where: path:line` rots (his own items already drift to bare `path`), so ours is `path` or `path:symbol`, and his verify-on-read step does the same job against a symbol. Added beyond both: a provenance line, since every one of his real items carries one anyway. The project-README-as-contract override is dropped with the index file it lived in — the format is fixed, so every invocation reads one predictable store. Migration for an existing `docs/issues/`: `issue` → `yes`, `open_decision` → `later`, `future_work` → `yes` or `later` by case; rename each file to a slug, drop the ID, and delete the README.
- add `log-issue` skill — captures a finding discussed in conversation into a standing issue register at `docs/issues/`, self-initializing the directory + README contract on first use. The register design comes from the mybaze repo's own `docs/issues/` (built during the 2026-08 rescue-plan work): one file per entry with a subsystem-prefixed ID, a three-part admission gate (real + re-derivable; needs an owner decision or deliberate deferral; not owned by a dated review), a body written for a reader without the conversation (concrete failure run, the misreading to prevent, options with costs, recommendation; symbols cited, line numbers banned — they rot), and **delete-on-resolution** (presence means open; the outcome lives in the ADR/plan/commit that records it). Deliberately minimal taxonomy — `issue | open_decision | future_work`, no severity field, no status machine: the richer FW-/ISS-/L/N machinery from dated review registers is review-triage, and carrying it into a standing register was considered and rejected. The project's own `docs/issues/README.md` is authoritative over the skill's bundled template, so a repo can evolve its register without the skill drifting.

It is the one Define-phase tool in that collection with a mechanism nothing else here reproduces: a one-question-at-a-time interview where **every question carries the agent's own guess**, opened by a one-sentence hypothesis with a confidence number, closed by an Outcome/User/Why now/Success/Constraint/**Out of scope** restate and an explicit yes — with "whatever you think is best", "sounds good" and silence each named as *not* a yes and re-asked. A single-agent gate and a self-refereeing loop are strictly weaker shapes for the same subject, so keeping them meant maintaining two answers to one question. `adr-review` was also never portable: it had a `## Step 3: The mybaze ADR shape` section and read `docs/adrs/*-dev-workflow.md` plus `.claude/rules/*.md` by name, so the knowledge in it belongs in the repo it was tuned for, as a versioned review profile beside that repo's other conventions — not in a marketplace plugin where every user inherits one project's filesystem layout. What is deliberately **not** removed is `check-likelihood`: a round needs a *filed* subject (a diff, a plan, an ADR, an issue file), and a claim raised three sentences ago is none of those, so the ad-hoc single-claim check has no replacement and is not made redundant by one.
- add `decision-brief` skill — the output format for the moment an agent stops and hands a fork back to the owner. It exists because the failure is asymmetric: the owner wrote the design while fully focused, the agent hits the judgement call days later, and a verdict assembled from section names, file paths, and internal terms asks them to reload the whole design from a pointer before they can read the question. Five parts, fixed order. **The story**: one concrete run in time order ending in the bad outcome, real values instead of variable names, 5–10 lines, with one clause stating whether it was *reproduced* or *derived from the design* — the two read identically and only one is evidence, so leaving it out silently upgrades a guess. **The step back**: 2–5 lines saying why this became possible and how far the same cause reaches (see the bullet below — this part is the whole reason the skill is not just a formatting rule). **The forks**: two to four, cheapest first, each priced both now and if added later, each **replaying** the same story to its new ending rather than summarizing it, each labelled *removes the cause* or *guards only*. **The recommendation**: one option, one question, answerable in a word, plus an offer to expand any fork — re-explaining costs the reader nothing while a pointer asks them to go read. **The pointers last**: one line, never at the top, never inside the story. Before any of it, the skill requires settling the problem rather than reaching for a guard: name the lock/retry/re-check you first wanted and what it leaves in place, run `/decide:check-likelihood` or a root-cause tool if present, and say plainly when the verdict is judgement rather than a checked result. Deliberately narrow: it does **not** fire for a failure the agent can fix itself, a yes/no on a step just described, work done in this session, or anything small and reversible, because a five-part brief on a two-minute fork spends exactly the attention the format protects. Harness-specific note: story, step back, and forks go in the message, the choice goes to `AskUserQuestion`, and each option description carries *what we do + cost + removes-or-guards* — a description that is itself a pointer defeats the format. It arrives as a skill rather than an output-style rule on purpose: it is heavyweight (a five-part procedure with worked examples) and it fires rarely, so as an always-on rule it spends constraint budget on every trivial turn and needs an exception clause to stop it over-firing — rarely-fired plus heavyweight plus procedural is the shape of a skill, while a default response shape that applies every turn is the shape of an output style. The five per-turn rules that came with it went to `Direct` instead (see Output styles above).
- `decision-brief`: **restore the step back as a visible part of the brief.** The upstream rule this skill was ported from ([`i-have-adhd`](https://github.com/pySilver/i-have-adhd) rule 11) had five parts, and part 2 was a root-cause pass run *before* proposing anything. The port kept the analysis and lost the artifact: it survived only as a pre-write instruction ("first, settle the problem"), with an explicit line telling the agent not to show the result — *"do not paste that verdict at the user: it is evidence for you"*. So the RCA ran in the agent's head and never reached the page, and the reader got what breaks (story) and what to do (forks) with no way to see **why the fork exists**. That gap is not cosmetic: a readable fork is still the wrong question when the fork itself is the artifact of an earlier bad split, and from inside a list of options the reader cannot tell which kind they are looking at, so choosing looks identical whether it is a decision or a patch over a design flaw. Part 2 now carries three things. **Why it became possible** — ask why until the answer is a decision someone made, not a line of code; one rung short returns the symptom wearing the word "cause" (*"the comparison uses the wrong side"* is where it shows), one rung long arrives at "we chose to have a database", and the output states where the ladder stopped rather than showing the ladder. **How far it reaches** — the birds-eye half, and new relative to upstream: does the same cause produce failures we have not hit yet, named, or is this the only place it can surface. Two options read very differently once the reader knows the same choice has four other exits. **One word**: `local` (the design was right, this build diverged from it — one line, then move on, and the expected answer most of the time), `design` (an earlier decision makes the condition possible), or `unknown` (could not trace it, plus the one thing that would settle it). Both failure directions are graded against: relabelling the defect line as the root cause, and manufacturing a design flaw so the section has something to say. When it lands on `design`, revising that decision **is** one of the forks — written, costed, and replayed like the others, not a "longer term we could" aside — and if it is genuinely off the table (already shipped, needs a migration, the release is Friday) that line goes where the fork would have been, because omitting it lets the menu imply it was never available. Recommending a guard after a `design` verdict is often right but now has to say why in the same breath, since a silent guard recommendation reads as a claim the cause was local. Second send check to match: can the reader tell whether picking from this menu is patching over something?
- add `plugins/decide/evals/` — four cases in the native `claude plugin eval` format (`evals/<case>/case.yaml`, schema 1.1), covering `decision-brief`. **Two of the four are negative on purpose**: the failure mode of a decision-brief format is over-firing, not under-firing, so a suite that only measures whether the five-part shape appears would score an over-firing skill as perfect. `decision-brief-fires` grades the shape on a real judgement call (walkthrough leads and is concrete; *reproduced* vs *derived* stated; a bounded step back that judges the *kind* of cause and its reach rather than restating the defect line; the cause separated from the row lock the prompt pre-offers, which is the one that catches a model repeating the prompt's framing back; 2–4 costed forks each **replaying** the scenario rather than summarizing its effect; one recommendation, one question; pointers on the last line). `decision-brief-cause-is-a-decision` is the step back's own case and is built to be the **opposite** of `decision-brief-fires` on exactly that axis: the prompt pre-frames the fork as a choice between two guards and states a favourite, and the real cause is an ADR the owner approved last week that put two writers on one column with last-write-wins — with two more columns exposed the same way and nobody has hit them yet. It grades that the cause comes back as the decision and not as "the guard is missing", that the unhit blast radius is named, that a revise-the-decision fork is written and costed and replayed alongside the two offered guards, and that the agent does not simply answer the question as asked. A skill that always reaches for "this is a design flaw" scores well on one positive case and badly on the other, which is the point. `decision-brief-silent-bounded-fix` and `decision-brief-silent-known-cause` assert silence on a known cause with a bounded fix. Graders are `llm` plus a few free `regex` ones; `runs: 3`; `execution.allowed_tools` deliberately empty, since every prompt is self-contained and the graders read the written answer. Run with `claude plugin eval decide@silver-cc-tools` — targeting by name adds the no-plugin baseline arm automatically, targeting a path needs `--ablation with-without`. Not wired into CI: it costs money and needs a live agent.
- `refine-plan-against-codex`: **a fix that succeeds can still introduce a defect, and the verify round was told not to look.** The hunt-once shape claims to keep the finding class that mattered — "round N's fix is wrong" — on the grounds that the verify round reads exactly that diff. That class has two halves and only one had a channel. A fix that *fails its own finding* returns `fixed: false` and stays on the list. A fix that *succeeds and introduces a different defect* cannot join the list at all (it may only shrink), so its only route out is `parked[]` — and the verify prompt said to park "a defect UNRELATED to any listed finding", which is precisely not what a defect living inside a fix's own new text is. Measured (2026-08-11, canonical-cluster-cutover): a fix correctly closed a "cross-row transition atomicity is undecided" finding by adding a section that decided it, and that new section specified a write order contradicting the codebase's single declared lock order — which the plan's own verified-facts block forbade inventing. The verify round returned `fixed: true` with an empty `parked[]`, the loop exited `completed_verified`, and a re-hunt found it immediately. The parked instruction now names the case explicitly (unrelated to every finding **or** created by a fix and living in the text that fix added), states that `fixed: true` must not suppress a second problem, and points the reviewer at the newest, least-reviewed text as the place to look hardest. Prompt-only: no new round, no new score, and `parked[]` stays reported-never-acted-on, so it cannot make the loop diverge — which is the property the whole hunt-once design protects. The SKILL's "what that keeps" paragraph is corrected to describe both halves and their different exits, and now says plainly that **`completed_verified` means "every listed finding is closed", never "the artifact is clean"** — the list going empty is a property of the list, not of the plan.
- `refine-plan-against-codex`: the convergence report now tells the operator to read a sub-gate finding for **self-contradiction**, not only for risk. Materialization scores how likely a triggering condition is to occur, which is the right question for a race or a limit and the wrong one for "the artifact contradicts an invariant it states about itself" — that scores low whenever the conditions are remote while still being worth fixing on sight, because it is cheap and the artifact is disagreeing with its own stated rule. From the same run: the lock-order finding scored `m=0.3`, honestly (the deadlock needs concurrent load; the project is pre-production), and the reason to fix it anyway had nothing to do with deadlock probability. One line in the report — deliberately not a third score, which would be a large change for one observation.
- `refine-plan-against-codex`: **hunt once, then verify — the loop now terminates by construction.** The previous shape re-reviewed the whole plan every round with codex's memory deliberately wiped, and that does not converge: "find what's wrong" is an unbounded generative task, each applied fix is new text for the next round to criticize, and a memory-wiped full re-review resamples the artifact instead of working down a list. The skill's own measurement said so — worst-finding severity by round on the brand-membership-propagation plan ran `0.42 -> 0.48 -> 0.86`, rising, because each round's best finding attacked the previous round's fix. That was read as "the value does not front-load, so do not stop early"; it is better read as evidence the process diverges, and no amount of filtering fixes a diverging process. Round 1 now hunts (unchanged prompt, unchanged arbiter and design routing) and produces a finite list. Rounds 2+ run a new **subagent #1b, the verifier**: scoped to `git show` of the previous round's commit, one `fixed: true|false` per open finding, and structurally forbidden from adding to the list. Anything else codex notices goes to `parked[]` — surfaced in the final report, deliberately never fixed, so noticing is cheap and acting on it stays a human decision. The open list only shrinks, giving a normal exit (`completed_verified`, new terminal status) instead of an exhaustion exit. What survives from the old shape is the finding class that actually mattered: a fix that reintroduces its own defect still returns `fixed: false`, because the verify round reads exactly that diff. What is dropped is "round 3 notices something unrelated in a section nobody touched".
- `refine-plan-against-codex`: consequences of the above. `MAX_ITER` drops from 20 to **4** (one hunt plus three verify passes) via the new `REFINE_PLAN_MAX_ROUNDS`; the cap is now a per-finding fix budget rather than a runaway guard, and raising it cannot buy another hunt. `ARBITER_FROM_ROUND` defaults to **1** instead of 4 — round 1 is the only round that produces findings, so it is the only round with anything to triage, and the old "trust codex for the high-value rounds 1-3" rationale disappears with the rounds it referred to. Verify rounds write codex's raw reply to `round-NN/verify.txt` and their parked items to `round-NN/parked.txt`, then **synthesize** `findings.txt` from the still-open original finding objects, so `parse_findings` / `summary` / `detect-stuck` keep working with no changes — and `detect-stuck` gains a sharper meaning: a `file:line` recurring across verify rounds is a finding the implementer *cannot fix*, not merely one codex keeps mentioning. The verify reply's fail-safe direction is the inverse of the arbiter's and deliberately so: a malformed arbiter reply treats every finding as real (silence must not drop a finding), while a malformed verify reply treats every finding as still open (silence must not declare one fixed and end the loop on a defect nobody checked). The cap-exit delta-check is kept and matters more at 4 rounds than at 20; `completed_verified` skips it, since its final round applied no fix. `state.py` gains only the new terminal status, covered by a new case in the bash suite. The verify prompt carries each open finding's full `body`, `instance`, and `cause` — not just its title and recommendation — because the verifier is a fresh process whose entire knowledge of a finding is that block; with only a title it can answer "does this edit resemble the recommendation?", and an edit can match the wording while leaving the failure intact, whereas `instance` (one concrete run with real values) turns the question into "does this diff make THAT run impossible?". That is deliberately the alternative to resuming codex's session across rounds: `codex exec resume` exists and would hand the verifier the hunter's memory along with the hunter's stake in its own recommendation, and of the two ways that fails — talked into its own fix, or defensive about its framing — the first is silent and ends the loop on a live defect, which decides it.
- `adr-review`: **drop the "only report issues you are confident about" instruction** — the Claude Opus 5 prompting guide states that conservative-report wording now suppresses recall (the model follows it literally and reports less). The agent already has the right filter: Step 5 scores every finding and routes weak ones to FYI. The closing rule now says report every real gap and let the tier do the filtering, instead of asking the reviewer to self-censor before scoring.
- `refine-plan-against-codex`: **the front-loading claim was backwards — corrected, and the cap exit now delta-checks the last fix.** The skill said the loop's value front-loads; measured on the brand-membership-propagation plan (2026-08-04) the curve ran the other way — worst-finding severity by round was 0.42 → 0.48 → 0.86, because each round's best finding attacked the previous round's fix (R3 caught a guard placed where three of four handlers bypass it). A reader who believed the old sentence stops early and ships the worse defect, so the text now states the observed behavior. Same observation closes the **last-fix hole**: under any cap exit the final round's fix is applied and never reviewed — the fix most likely to be wrong. On `completed_cap` the orchestrator now runs one scoped delta-check (subagent #1 over the final round's commit diff only) and reports its findings verbatim without applying them, since applying would recreate the same hole one fix later. Also adds an explicit **prompt-neutrality rule** to the codex-asker contract: substitute the two placeholders and change nothing else — a round framed with "over-planning is a defect here" + "a prior pass verified this design" returned approve with zero findings, while the identical file under the neutral prompt returned three, including a high. Scope discipline belongs in the orchestrator's triage, never in codex's prompt.
- `adr-review`: **verify the ADR's factual premises against the source** — the agent reviewed decision quality (decided? alternatives weighed? consequences named?) but had no duty to check whether the ADR's claims about existing code are *true*, despite already holding Grep/Read/Bash. That gap cost a Stage-5 rework three separate times (a nonexistent CAS re-read recorded as "kept, load-bearing"; a "two writers" column that had three; a re-import reset that never happens). New Critical checklist item: every factual premise about existing code — a symbol exists, a guard runs, N writers/callers, a field carries X — is verified by reading the source, and a premise that does not hold is a finding. When the ADR *enumerates* writers/callers/call sites, the count is grepped before it is accepted (that shape produced two of the three failures). Authors are asked to state premises with `file:line` provenance so the check is mechanical. The two failure classes stay separate: a wrong decision escalates to the owner, a wrong fact is corrected in place — a bad decision needs the owner, but a bad fact needs a grep.
- `refine-plan-against-codex`: **ask what caused the condition before pricing a guard** — the same discipline `check-likelihood` applies ad hoc, brought into the loop. Codex now fills `cause` (the plan decision that makes the condition possible), `instance` (one concrete run that ends badly, with real values — "worker 2 picks up order 8814 while worker 1 is still writing it", not "two workers race on a row", since a condition is checkable and an instance is imaginable), and `fix_kind`: `guard` when the recommendation adds a check, retry, lock, or branch that holds the symptom down, `design` when the condition only exists because of a choice the plan already made. From round 4 the arbiter answers `fix_kind` independently and overrides, because Codex has an incentive to say `guard` — it is the smaller edit and it keeps the recommendation inside the implementer's licence. Design findings are **routed to the user, never to the implementer**: subagent #2's "findings are the only license to edit" rule is what stops the loop wandering, and restructuring a plan is the opposite of a minimum-scope edit, so letting it decide would trade a real safeguard away. Four options (revise the plan yourself → new terminal status `completed_design_handoff`; widen the licence for those findings only, recorded in the round's commit; accept the guard and knowingly leave the cause; or ignore). Without this the loop bolts a lock onto a two-writer design, marks the finding resolved, and carries the cause forever — every round making the plan worse while reporting progress. `state.py` gains only the new terminal status; the rest is prompt and orchestration contract.
- **`materialization` scoring across both reviewers** — a 0–1 score answering "if this ships as written, how likely is it that the flagged issue actually bites?", orthogonal to `confidence` ("is the claim true?"). Both Codex and Claude-family reviewers produce an endless supply of technically-correct findings whose triggering conditions will realistically never occur, and neither `severity` (a rare bug is still severe *if* it fires) nor `confidence` can filter them. Now they get scored and filtered:
  - `refine-plan-against-codex`: Codex self-scores every finding from round 1; from round 4 the arbiter re-scores each one **blind to Codex's number** and its score overrides. Two thresholds with two jobs — `MATERIALIZATION_FLOOR` (env `REFINE_PLAN_MATERIALIZATION_FLOOR`, default `0.3`) keeps sub-floor findings out of the implementer, and `MATERIALIZATION_GATE` (env `REFINE_PLAN_MATERIALIZATION_GATE`, default `0.5`) is the bar a real `high`/`critical` must clear to keep the loop alive (below it, still fixed — just no extra round). Nothing is dropped silently: `↓Nm` appears on the codex-done line and in the summary table, the arbiter row gains an `m<max>` digest, and the convergence report names every gated finding with its score and the arbiter's condition sentence. Both prompts also separate *unverifiable* from *unlikely* — when the plan doesn't state the constraint that would settle a condition, the reviewer scores `1.0` and names the missing information instead of guessing low, since the floor filters before the implementer ever sees the finding. A missing or unparseable score reads as `1.0` everywhere, so an absent number never drops a finding and arbiter silence can never converge the loop — resuming a pre-materialization run behaves exactly as before. `state.py` reads the same floor env var, so `summary` / `detect-stuck` never disagree with the loop; `detect-stuck` consequently stops prompting about locations that only recur below a floor. New coverage in both the Python and bash suites (floor filtering, `_score` fail-safe direction, env override incl. garbage/out-of-range fallback, the `↓Nm` and `m<max>` digests).
  - `adr-review`: every Critical/Important finding must now carry a materialization score and the condition that triggers it. Two binding rules replace reviewer instinct — below `0.30` a finding is demoted to **FYI** whatever its severity, and a Critical needs `≥ 0.50`. `NEEDS REVISION` therefore requires at least one finding above the floor: an ADR whose findings are all Nit/FYI is `APPROVE` with a note, instead of being held up by a list of things that will never happen. Scoring splits into three explicit cases, because collapsing them is how a review buries a real finding: **can't name the condition** → not established, drop to FYI; **can name and check it** → score normally; **can name but can't check it** (it turns on a constraint the ADR doesn't state) → mark `materialization: unverified`, keep the severity, name what would settle it, and do *not* downgrade on a guess. The two hard rules apply to scored findings only, so an unverified finding keeps the decision open rather than waving it through — guessing low and guessing high are the same error, but only guessing low is silent.
- `refine-plan-against-codex`: lower the default Codex reasoning effort from `xhigh` to `high` in `run-codex.sh` — `high` is the intended default for our Codex calls; `xhigh` spent extra latency/tokens without proportional gain. The model default (`gpt-5.6-sol`) and the `CODEX_MODEL`/`CODEX_NO_OVERRIDES` escape hatches are unchanged.
- `adr-review`: pin the reviewer to `model: opus` (version-less alias, so it always resolves to the current Opus) instead of inheriting the session model. ADRs are usually authored by the session model (often Fable), so an inherited reviewer is the same model grading its own work — a fixed Opus reviewer gives an independent second perspective on the decision.

### git

- `finalize-feature-branch`: **a landing lock keeps two worktrees on one machine from finalizing at once.** After "Proceed", finalize creates `finalize-feature-branch.lock` in the git common directory, which every worktree of the repository shares, with `mkdir`, which either creates it or fails. It writes its branch, worktree and start time into an `owner` file inside. A second finalize that finds the lock held stops and offers to rerun once the owner's branch lands, or to break it; a lock whose branch has already landed or whose worktree is gone is offered as stale. It never waits by sleeping or polling. Every stop after the lock was taken releases it, and so does the end of step 11, before the wrap-up offer. The failure it prevents is a lane rebasing onto a default branch another lane is about to move, then failing its push or rerunning a 20-45 minute suite. The input is two lanes finalizing at once on one host, and it happened in a run of 2026-10-29; without the lock that cost one rerun, with both suites slowed by CPU and database contention. Pushes from other machines are not covered; the plain non-force push still refuses those.
- `finalize-feature-branch`: **a full-suite pass recorded by a peer-planning run counts.** Finalize skipped the suite only after a full run passed in its own session, so finalize from a fresh session, which `exec` now recommends, always ran the whole suite again. It now also accepts a `FULL-SUITE PASS` line in a `.peer-planning/*/progress.md` of this worktree or of the main checkout, when the line's SHA is exactly the branch's head before finalize rebased and collapsed it, the working tree was clean then and is clean now, and passed + skipped equals collected. The documentation-only rule for what the rebase pulled in still applies. Any commit after the recorded one, a review fix among them, makes the record name an older commit, and the suite runs. A recorded pass is one another session saw, and the report says so.
- **add `wrap-up`.** Finalize landed the branch and left the rest to hand-typed cleanup: the worktree and its branch, the test database `scripts/setup-worktree.py` had created, the plan still under `docs/plans/`, the peer-planning run record and its monitor session. `/git:wrap-up [branch]` does that in one go after confirming the branch is an ancestor of the remote default branch, with every item shown as a ticked checklist before anything is removed; the plan is archived with the project's `docs(plans): <title>, completed` rename commit, the worktree is never force-removed, and a session inside the worktree gets the removal commands printed instead of a vanished working directory. It ends with the main repository's stranded-container scan. From the main checkout with no argument it offers every worktree whose branch has landed.
- `finalize-feature-branch`: **offers the wrap-up after a landing**, and says deleting the branch is the wrap-up's job rather than nobody's.
- `finalize-feature-branch`: **land from a worktree by pushing to the remote default branch, since the local merge is not available there.** When another worktree has the default branch checked out, that branch is locked to it: `git checkout <default>` fails with `already used by worktree at ...`, and `git fetch . HEAD:<default>` refuses for the same reason — so the old first option was simply unreachable for anyone finalizing inside a worktree. Step 11 now reads `git worktree list --porcelain` first and, in that case, offers `git push origin HEAD:<default>` as the default action instead. It is the same landing, one hop earlier: HEAD was rebased onto `origin/<default>` in step 5, so the remote sees a fast-forward, and the push stays plain — the remote's own non-fast-forward refusal is the wanted safety net, exactly as in the local path. Two things it deliberately does not do: move the ref with `git update-ref`/`git branch -f` (the other worktree's index would still describe the old commit, so that checkout would come up looking like every file the branch added had been deleted), and silently fast-forward that worktree — it reports the path as behind, and only offers to run `git -C <path> merge --ff-only origin/<default>` when `status --porcelain` there is empty, because that command changes files in a checkout the user may be sitting in.
- `finalize-feature-branch`: **the default landing action is now merge-into-default-and-push, not publish-the-feature-branch.** The old final step offered `--force-with-lease` on the feature branch or nothing, which serves a PR flow; the common flow here is rebase, fold to one commit, fast-forward into the default branch, push that. Both are offered, with merge first. The merge path checks the local default branch is not diverged, requires `--ff-only` (HEAD was just rebased onto `origin/<default>`, so a fast-forward is the only correct outcome — if git refuses one, something moved underneath and a merge commit would hide it), and **never force-pushes the default branch**: a rejected push means someone else pushed while you worked, so the run stops and reports rather than retrying with force. The checkout is left on the default branch and the report says so; deleting the feature branch stays out of scope.
- `finalize-feature-branch`: **skip the full test suite when the rebase pulled in documentation only.** The finalize step changes no code by itself — `git reset --soft` + commit rewrites history, not the tree — so the only thing that can break an already-verified branch is upstream work arriving under it. The skill now diffs the pre-fetch merge-base (`git merge-base HEAD origin/<default>`, recorded in the preview step because it is unrecoverable after the fetch) against the new default-branch tip, which is the right comparison: the naive one, whether `git fetch` moved anything, misses a branch that was already several commits behind and gets rebased onto genuinely new code. Skipping requires all three of empty-or-docs-only incoming set, a conflict-free rebase (a resolved conflict is code nothing has ever run), and a full suite that already passed this session against the same feature-branch code.
- `finalize-feature-branch`: `.md` does **not** imply documentation, and the classifier says so explicitly — this marketplace is its own counter-example, since `skills/*/SKILL.md` is the shipped product, not prose about it. Four named never-doc overrides that beat the extension: anything under `tests/`/`fixtures/`/`__snapshots__/` and friends (an assertion can read that prose), dependency and build manifests wearing doc extensions (`requirements*.txt`, `CMakeLists.txt`, `MANIFEST.in`), markdown a repo ships as source rather than prose, and markdown/rst executed as doctests (grep for `--doctest-glob` or a Sphinx `doctest` builder before deciding). Anything matching neither list is unclassified, and unclassified is explicitly *not* documentation. The fail-safe direction is one-way on purpose — every uncertainty runs the suite, and an unclassifiable file or a stale-looking session run raises an AskUserQuestion instead of a guess. A skip is never silent: the report carries the incoming file list and names the earlier run it relies on, because the skip is a claim about coverage and the operator is the one who has to believe it.
- `finalize-feature-branch`: add `AskUserQuestion` to `allowed-tools`. The skill has directed the model to use it since it was written and it was never declared.
